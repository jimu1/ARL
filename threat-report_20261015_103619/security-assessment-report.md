## 二、功能概述

本需求为在现有 ARL 系统（Python / Flask + flask-restx + MongoDB）中**新增「用户通过邮箱注册」功能**。

**分析时的项目现状（证据）：**

- 现有用户接口位于 [app/routes/user.py](app/routes/user.py)，仅包含 `POST /user/login`、`GET /user/logout`、`POST /user/change_pass`，**目前没有任何注册入口**。
- 用户数据存储于 MongoDB `user` 集合，读写逻辑见 [app/utils/user.py](app/utils/user.py)。
- 现有密码存储方式为 `gen_md5(salt + password)`，盐值为**全局固定字符串** `arlsalt!@#`（[app/utils/user.py:7](app/utils/user.py#L7)、[app/utils/user.py:13](app/utils/user.py#L13)）。
- 现有登录态为 `gen_md5(random_choices(50))` 生成的 Token，存于用户记录并由 `Token` 请求头携带。
- 用户模型中**目前不存在 email 字段**，注册功能需要新增邮箱字段、邮箱唯一性约束、验证码/验证链接存储等。

**本次威胁建模覆盖的安全域：**

- [x] 身份认证（账号创建、口令策略、凭据存储）
- [x] 验证码（邮箱验证码/验证链接的发送与校验）
- [x] 敏感数据（邮箱存储、脱敏、日志）
- [x] 业务安全（注册接口防滥用、防爆破、防轰炸）
- [x] 安全日志（注册、验证、失败审计）
- [ ] 权限管理（注册为匿名接口，暂不涉及，但需防止越权写用户集合）
- [ ] 文件操作 / 交易支付（不涉及）

**预期业务流程（假设，需与产品确认）：**

1. 用户提交邮箱 → 后端校验格式与唯一性 → 发送验证码/验证链接；
2. 用户提交验证码/点击链接 → 后端校验；
3. 用户设置密码 → 后端创建账号（校验前两步结果）；
4. 注册成功，可登录。

> ⚠️ 上述流程为基于需求的合理推定；若实际流程不同（如"先设密码后验证""无需邮箱验证直接注册"），部分威胁的风险等级需重新评估。

## 三、识别的威胁场景

| 序号 | 威胁类型 | 风险等级 | 相关知识库 | 威胁描述 |
|-----|---------|---------|-----------|---------|
| T1 | 注册验证流程缺失/可绕过（验证凭证未与邮箱绑定、步骤可跳过） | 🔴 高 | `02-authentication.md` 5.1 / `03-authorization.md` 3 | 参照密码找回的典型案例：注册最终落库接口若不校验前序"邮箱+验证码"的验证结果，或验证码与邮箱未做绑定校验，攻击者可用自己邮箱收到的验证码为**任意邮箱**完成注册，实现邮箱归属伪造/账号接管 |
| T2 | 密码弱哈希存储 | 🔴 高 | `06-sensitive-data.md` 2 | 若沿用现有 `gen_md5(salt+password)`（MD5 + 全局固定盐，见 `app/utils/user.py:7,13`）存储注册口令，一旦数据库被拖库，全部用户口令可被彩虹表/GPU 秒破，属于严重数据泄露 |
| T3 | 邮箱验证码可爆破 | 🟡 中 | `04-captcha.md` 2 | 验证码位数不足、验证次数不限、有效期过长或验证成功后不失效，攻击者可爆破验证码完成非本人邮箱注册 |
| T4 | 邮件轰炸 / 批量注册（接口无频率与防爆破） | 🟡 中 | `04-captcha.md` 2 / `07-business-security.md` 3 | 发送验证码接口可被重放，对目标邮箱发起邮件轰炸；注册接口无频率限制可被脚本批量注册，消耗资源并污染用户库 |
| T5 | 邮箱/账号枚举 | 🟡 中 | `07-business-security.md` 3.3 | 注册或找回接口对"邮箱已存在/不存在"返回差异化的明确提示，攻击者可批量探测系统内已注册用户，造成信息泄露 |
| T6 | 邮件模板注入 / 内容注入 | 🟡 中 | `04-captcha.md` 2 | 若邮件正文模板使用用户可控字段（如昵称、邮箱前缀）拼接且未转义，攻击者可借平台发送钓鱼域名/黄赌毒内容 |
| T7 | 邮箱明文存储与明文日志 | 🟡 中 | `06-sensitive-data.md` 1/2 / `09-security-logging.md` | 邮箱属客户敏感数据，明文落库与明文打印进日志（含响应回显）会扩大泄露面；返回给前端也不应无条件回显明文 |
| T8 | 接口未鉴权 / 传输未加密 | 🟡 中 | `07-business-security.md` 3 | 注册相关接口（发送验证码、提交注册）必须走 HTTPS（TLS 1.2+）；同时应防止通过 JS 直接构造请求越权写入 `user` 集合 |
| T9 | 安全日志缺失 | 🟢 低 | `09-security-logging.md` 3 | 注册成功、验证码校验失败、频率拦截等关键事件未记录，不利于安全审计与溯源 |
| T10 | 错误信息过于详细 | 🟢 低 | `07-business-security.md` 3 / `02-authentication.md` | 接口返回堆栈、SQL/数据库错误或内部字段名，暴露技术栈与内部结构 |

**风险等级判定依据**：影响程度与发生概率参照 `references/risk-assessment-matrix.md`（未授权/越权写、批量拖库口令 → 高风险；验证码可爆破、账号枚举、轰炸 → 中风险；日志/报错细节 → 低风险）。

## 四、安全需求清单

### 🔴 高优先级（必须实现）

#### 1. 注册流程逐步校验且验证凭证与邮箱强绑定（对应 T1）

**需求描述**：注册流程的每一步验证结果必须与后续步骤关联，禁止跳过任一步骤。校验（验证码/验证 Token）必须与目标邮箱绑定，不允许"用 A 邮箱的验证码注册 B 邮箱"。

**验收标准：**
- [ ] 发送验证码接口与校验接口之间，服务端保存 `邮箱 → 验证凭证` 的绑定关系（服务端会话/Redis），不依赖前端传入的邮箱参数作为唯一依据；
- [ ] 落库创建账号时，后端再次校验步骤 1、步骤 2 的验证结果均已完成且未过期；
- [ ] 修改顶层邮箱参数后，原验证码立即失效（无法用于新邮箱）；
- [ ] 验证凭证一次性使用，验证成功后立即失效。

**参考**：`02-authentication.md` 5.1；`03-authorization.md` 3

---

#### 2. 口令采用强哈希 + 每用户独立盐存储（对应 T2）

**需求描述**：**不得沿用现有 `gen_md5(salt+password)` 全局固定盐方案**。新注册口令必须使用抗暴力破解的自适应哈希（bcrypt / Argon2id / PBKDF2，迭代/代价参数符合当前推荐值），每个用户使用独立随机盐。

**验收标准：**
- [ ] 口令哈希使用 bcrypt/Argon2id/PBKDF2 之一，禁止 MD5/SHA1/单轮 SHA256；
- [ ] 每用户独立随机盐（由哈希算法内嵌管理），禁止使用全局固定盐；
- [ ] 全局搜索确认新代码中不出现 `gen_md5(salt + password)` 形式的存储（存量兼容方案需单列说明）；
- [ ] 口令在同一系统内不得明文出现于数据库、日志、响应包中。

**参考**：`06-sensitive-data.md` 2；`02-authentication.md`

---

### 🟡 中优先级（建议实现）

#### 3. 邮箱验证码安全策略（对应 T3）

**需求描述**：验证码需具备足够的抗爆破强度。

**验收标准：**
- [ ] 验证码位数 ≥ 6 位（或采用高熵随机 Token 链接）；
- [ ] 同邮箱验证码错误尝试达 3 次后验证码立即失效，需重新获取；
- [ ] 验证码有效期 ≤ 5 分钟；
- [ ] 验证码验证成功一次后立即失效；
- [ ] 验证码**不在响应包中回显**，生成与校验均在后端完成。

**参考**：`04-captcha.md` 2

---

#### 4. 注册与发码接口防滥用（对应 T4）

**需求描述**：防止邮件轰炸与批量注册。

**验收标准：**
- [ ] 单邮箱发送验证码接口：60 秒内限 1 次，单日上限受限（如 ≤10 次）；
- [ ] 单 IP / 单设备对发码与注册接口做频率限制与滑块或图形验证码前置校验；
- [ ] 注册接口对同一 IP 的创建速率做限制（如 N 次/小时），异常时告警；
- [ ] 发码接口具备幂等或重放保护，防止直接重放请求造成轰炸。

**参考**：`04-captcha.md` 2；`07-business-security.md` 3

---

#### 5. 抑制邮箱/账号枚举（对应 T5）

**需求描述**：注册及后续找回接口对"邮箱是否已注册"的响应应保持一致，避免账号枚举。

**验收标准：**
- [ ] 无论邮箱已存在与否，发码接口返回的响应文案、状态码、响应时间一致（如统一提示"若该邮箱可用，我们已发送验证邮件"）；
- [ ] 错误提示不区分"邮箱不存在"与"验证码错误"；
- [ ] 接口响应时间做常量级处理或异步发送，避免时序差异被利用。

**参考**：`07-business-security.md` 3.3

---

#### 6. 邮件模板禁止注入用户可控内容（对应 T6）

**需求描述**：邮件正文/主题不得拼接未转义的用户输入。

**验收标准：**
- [ ] 邮件模板使用静态文案，用户可控字段（昵称/邮箱前缀）不进入正文；
- [ ] 如必须使用动态字段，须做 HTML 转义与白名单校验，禁止传入 URL/域名等可被钓鱼利用的内容；
- [ ] 邮件正文中的链接域名必须为固定白名单域名，不接收用户参数拼接。

**参考**：`04-captcha.md` 2

---

#### 7. 邮箱最小化存储、脱敏与日志安全（对应 T7）

**需求描述**：邮箱按敏感数据处理，遵循"非必要不展示明文"，避免落库/日志/响应过度暴露。

**验收标准：**
- [ ] 数据库存储按公司规范评估加密（加密机）或至少访问受限，禁止明文批量展示；
- [ ] 前端/接口展示时按脱敏规则处理（如 `w*******@qq.com`）；
- [ ] 应用日志、异常堆栈中不出现完整邮箱明文与验证码明文；
- [ ] 接口仅返回业务所需最少字段，不返回密码哈希、内部 ID 等无关字段。

**参考**：`06-sensitive-data.md` 1/2

---

#### 8. 传输安全与接口边界（对应 T8）

**需求描述**：注册相关接口必须加密传输，并限制对 `user` 集合的写入路径。

**验收标准：**
- [ ] 所有注册/发码接口强制 HTTPS，服务端禁用 TLS 1.0/1.1 与 SSLv2/v3；
- [ ] 注册接口不信任前端传入的角色/权限字段（如 `type`、`is_admin`），服务端固定为普通用户；
- [ ] 服务端对 `user` 集合的写入仅经由受控的注册服务，禁止通过其他接口间接写入；
- [ ] 注册接口对请求体做严格字段白名单校验，拒绝多余字段。

**参考**：`07-business-security.md` 3

---

### 🟢 低优先级（酌情实现）

#### 9. 注册与验证安全日志（对应 T9）

**需求描述**：记录注册相关的关键安全事件，便于审计。

**验收标准：**
- [ ] 记录注册成功（含操作人标识、邮箱脱敏值、时间、来源 IP）；
- [ ] 记录验证码校验失败、频率拦截、重复注册尝试等异常事件；
- [ ] 日志中邮箱/验证码做脱敏或哈希处理，避免日志本身成为泄露源。

**参考**：`09-security-logging.md` 3

---

#### 10. 统一错误响应（对应 T10）

**需求描述**：对外错误信息不得暴露堆栈或内部结构。

**验收标准：**
- [ ] 生产环境关闭 debug，统一封装异常，返回通用错误码与文案；
- [ ] 不返回异常堆栈、数据库错误原文、内部字段名。

**参考**：`07-business-security.md` 3

## 五、安全日志要求

| 操作类型 | 是否需要日志 | 日志类型 | 备注 |
|---------|------------|---------|------|
| 发送注册验证码 | 是 | 通用安全日志 | 记录脱敏邮箱、来源 IP、时间、结果 |
| 注册成功 | 是 | 通用安全日志 | 记录脱敏邮箱、时间、IP；不记录口令与验证码明文 |
| 验证码校验失败 | 是 | 通用安全日志 | 记录失败次数与来源，用于爆破检测 |
| 注册频率拦截 | 是 | 通用安全日志 | 记录触发限流的 IP/邮箱（脱敏） |
| 邮箱明文查看/导出 | 视业务 | 埋点日志 | 若提供后台批量查看用户邮箱，需记录 view/下载 埋点 |

## 六、检查清单汇总

### 通用检查项
- [ ] 注册功能是否经过安全评审？
- [ ] 是否制定注册/验证相关的安全测试用例（含爆破、绕过、轰炸场景）？
- [ ] 上线前是否进行渗透测试？

### 功能特定检查项
- [ ] 注册落库接口是否二次校验前序邮箱+验证码结果，且凭证与邮箱绑定？（T1）
- [ ] 口令是否使用 bcrypt/Argon2id/PBKDF2 + 每用户独立盐，未沿用 `gen_md5(salt+password)`？（T2）
- [ ] 验证码 ≥6 位、3 次错误失效、有效期 ≤5 分钟、一次有效、不回显？（T3）
- [ ] 发码/注册接口是否有频率限制与滑块或图形验证码？（T4）
- [ ] 发码接口响应是否无法区分邮箱是否已注册？（T5）
- [ ] 邮件模板是否禁止拼接用户可控内容与自定义链接域名？（T6）
- [ ] 邮箱是否脱敏展示，日志与堆栈是否不含邮箱/验证码明文？（T7）
- [ ] 接口是否强制 HTTPS（TLS 1.2+），注册是否固定普通用户角色、按白名单收字段？（T8）
- [ ] 注册成功、验证失败、限流拦截是否记录安全日志？（T9）
- [ ] 生产环境错误返回是否已统一封装、不暴露堆栈？（T10）

## 七、局限性

1. **业务规则未确认**：注册流程（是否强制邮箱验证、是否需要邀请码、是否有组织/角色概念）为基于需求的合理推定，实际流程若不同，T1、T4、T8 的风险等级与需求需重评。
2. **未读取完整代码库**：本次仅读取了与用户相关的 [app/routes/user.py](app/routes/user.py)、[app/utils/user.py](app/utils/user.py) 及目录结构；未评估邮件发送通道、限流中间件、网关鉴权、MongoDB 账号权限等外围实现。
3. **未评估存量数据**：现有 `user` 集合的存量口令仍为 MD5+固定盐，本报告只约束新增注册功能；存量口令加固（强制改密/迁移）需单独立项。
4. **未做运行时验证**：本报告为设计阶段威胁建模，未对运行实例进行实际渗透验证，所有结论基于代码与知识库推断。
5. **合规项未覆盖**：邮箱加密存储涉及公司加密机规范与《个人信息保护法》合规，需与安全/合规团队确认具体落地方式（是否强制加密机、是否需隐私政策告知与用户同意）。
